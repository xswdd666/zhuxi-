# 筑析 AI｜四页面交互产品开发交接

## 1. 任务目标

基于 `前端页面/` 中的四张已确认设计图，升级当前 FastAPI + SQLite + 原生 HTML Demo，使页面中的核心按钮都有真实接口、明确返回状态和完整门禁。

设计源文件：

1. `前端页面/筑析AI-项目资料-定向删减版.png`
2. `前端页面/筑析AI-资料审核-卡片列表版.png`
3. `前端页面/筑析AI-问题与策略-三选项加自定义.png`
4. `前端页面/筑析AI-汇报生成-含汇报稿.png`

主流程：

```text
项目资料
→ 上传并解析资料
→ 生成带来源洞察
→ 用户审核并确认
→ 选择问题
→ 生成并选择策略
→ 生成汇报草稿
→ 编辑结构
→ 导出 Markdown
```

完成标准不是“页面看起来相似”，而是：每个主按钮都能产生真实、可持久化、可恢复、可理解的结果。

## 2. 开发边界

固定技术范围：

- Python 3.11；
- FastAPI；
- SQLite；
- 原生 HTML、CSS、JavaScript；
- DeepSeek 文本与视觉模型；
- Ollama `qwen3-embedding:0.6b`；
- ChromaDB 本地持久化；
- LangGraph `StateGraph`，在后续阶段接入。

本轮不做：

- 登录、注册和多人权限；
- Vue、React、Next.js 等前端框架迁移；
- 云部署；
- BIM、CAD、复杂 OCR；
- 自动建筑方案或专业规范审查；
- 为视觉效果大规模重构后端；
- 与四个设计页面无关的功能扩展。

优先级：真实闭环 > 门禁与异常 > 数据恢复 > 视觉细节。

## 3. 全局交互规则

所有按钮必须至少覆盖以下状态：

```text
idle      默认可操作
disabled  门禁不满足，并显示原因
loading   请求执行中，按钮防重复点击
success   返回结果、数量、时间或下一步入口
error     显示可读错误和重试入口
```

统一错误格式：

```json
{
  "error": {
    "code": "GATE_BLOCKED",
    "message": "请先确认至少一张洞察卡。",
    "details": {}
  }
}
```

关键门禁：

- 只有 `confirmed` 洞察能进入问题生成；
- `edited` 洞察必须再次确认；
- 问题必须关联确认洞察，或标记为 `hypothesis`；
- 用户必须选择问题后才能生成策略；
- 每个问题默认只能选中一条策略；
- 汇报只使用确认洞察、关联问题和已选策略；
- 未确认洞察、已驳回洞察和未选策略不能进入正式汇报。

## 4. 页面一：项目资料

### 4.1 项目基础信息

页面字段：

- 项目名称；
- 项目类型；
- 项目地点；
- 项目阶段；
- 任务目标；
- 场地标签。

扩展 `projects`：

```text
location TEXT
stage TEXT
objective TEXT
tags_json TEXT
updated_at TEXT
```

新增：

```http
PATCH /api/projects/{project_id}
```

请求示例：

```json
{
  "name": "滨水文化中心改造",
  "project_type": "既有建筑改造",
  "location": "杭州市拱墅区·运河沿岸",
  "stage": "前期资料分析",
  "objective": "梳理现状条件并形成设计问题依据",
  "tags": ["既有改造", "滨水场地"]
}
```

“保存草稿”返回：

- 保存后的 Project；
- `updated_at`；
- 页面显示“草稿已保存”；
- 请求失败时保留用户输入。

### 4.2 文件上传

现有接口继续使用：

```http
POST /api/projects/{project_id}/documents
GET  /api/projects/{project_id}/documents
```

上传返回必须展示：

- 文件名；
- 文件类型；
- 上传/解析状态；
- RAG `ready/degraded`；
- 失败原因；
- 已索引 Chunk 数量。

单个文件失败不能阻塞其他文件。

当前代码不支持 DOCX。二选一：

1. MVP 最快方案：从页面删除 DOCX 支持文案；
2. 如保留 DOCX：安装 `python-docx` 并补真实解析和验收。

### 4.3 文件操作菜单

“…”菜单第一版只保留：

- 查看解析片段；
- 重新解析；
- 删除文件。

新增：

```http
GET    /api/documents/{document_id}/chunks
GET    /api/documents/{document_id}/preview
POST   /api/documents/{document_id}/retry
DELETE /api/documents/{document_id}
```

删除文件时同步：

- 删除 SQLite Document 和 SourceChunk；
- 删除 Chroma 中对应 `document_id` 的向量；
- 删除本地上传文件；
- 若洞察已引用该文件，禁止直接删除并返回引用数量，或要求用户先确认级联影响。

不得把后端绝对文件路径返回前端。

### 4.4 提交资料并生成洞察

继续使用：

```http
POST /api/projects/{project_id}/insights:generate
```

按钮执行过程：

```text
点击
→ 按钮进入 loading 并禁止重复点击
→ 显示“正在解析资料/生成洞察”
→ 成功返回洞察数量、mode、message
→ 跳转或引导进入资料审核
```

防重复要求：

- 同一次点击不得重复提交；
- 再次生成时，不得无提示地重复插入完全相同的 pending 卡；
- 最小方案可在响应中返回 `created_count`、`skipped_count`。

### 4.5 场地图片预览

使用文档预览接口返回图片内容，不直接暴露本地 `path`。

图片观察仍须标记：

```text
source_type=image_observation
review_status=pending
```

视觉模型结果不能自动成为已确认事实。

### 4.6 任务记录

`task_logs` 表已存在，新增：

```http
GET /api/projects/{project_id}/task-logs
```

返回：

```json
{
  "logs": [
    {
      "id": "...",
      "task_type": "graph.diagnostician",
      "status": "completed",
      "message": "检索 5 个资料片段，生成 2 张问题卡。",
      "created_at": "..."
    }
  ]
}
```

页面底部“任务记录”点击后展开时间线。不能返回 API Key、完整敏感资料或后端绝对路径。

## 5. 页面二：资料审核

### 5.1 分类和统计

使用现有接口：

```http
GET /api/projects/{project_id}/insights
```

以下内容前端计算即可：

- 待确认数量；
- 已确认数量；
- 待核实数量；
- 全部、场地事实、设计约束、用户诉求、信息缺口筛选。

筛选无结果时显示明确空状态。

### 5.2 卡片审核

继续使用：

```http
PATCH /api/insights/{insight_id}
```

操作映射：

| 按钮 | 请求状态 | 成功后的页面状态 |
|---|---|---|
| 确认并用于下游 | `confirmed` | 更新卡片、数量和下游门禁 |
| 修改 | `edited` | 保存内容并提示“需再次确认” |
| 驳回 | `rejected` | 卡片退出可用事实集合 |
| 待核实 | `needs_verification` | 保留卡片，但禁止进入下游 |

修改表单支持：

- 标题；
- 正文；
- 分类。

### 5.3 来源定位

扩展 `Source`：

```text
source_chunk_id
```

新增：

```http
GET /api/source-chunks/{chunk_id}
```

点击“来源”后弹出侧边抽屉，展示：

- 文件名；
- 页码/片段位置；
- 原始 Chunk；
- 引用原文高亮；
- 图片观察时显示原图和 observation。

## 6. 页面三：问题与策略

### 6.1 问题选择持久化

扩展 `problem_cards`：

```text
selected INTEGER NOT NULL DEFAULT 0
updated_at TEXT
```

扩展 Problem Schema：

```json
{
  "selected": true
}
```

新增：

```http
PATCH /api/problems/{problem_id}
```

请求：

```json
{"selected": true}
```

刷新页面后，问题选择必须从 SQLite 恢复，不得只保存在 localStorage。

问题证据展示可以由前端根据 `linked_insight_ids` 与已加载洞察进行关联；不必重复存储来源文案。

### 6.2 策略生成

继续使用：

```http
POST /api/projects/{project_id}/strategies:generate
```

只允许传入当前项目中 `selected=true` 且 `status=ready` 的问题。

重复生成策略时：

- 已选策略不得被静默覆盖；
- 推荐返回已有策略，或只替换该问题下未选择的 AI 策略；
- 响应说明是 `created`、`reused` 还是 `regenerated`。

### 6.3 策略单选

设计图使用单选圆圈，因此后端必须保证：同一个 `problem_id` 最多只有一张 `selected=true` 策略。

继续使用或扩展：

```http
PATCH /api/strategies/{strategy_id}
```

当某策略设为 `selected=true` 时，在同一 SQLite 事务中把同问题其他策略设为 false，再返回该问题的全部策略或最终选中 ID。

### 6.4 自定义策略

扩展 `strategy_cards`：

```text
is_custom INTEGER NOT NULL DEFAULT 0
updated_at TEXT
```

新增：

```http
POST  /api/problems/{problem_id}/strategies
PATCH /api/strategies/{strategy_id}
DELETE /api/strategies/{strategy_id}
```

自定义策略必须填写：

- 策略名称；
- actions；
- preconditions；
- tradeoffs；
- validation_items。

自定义策略也必须通过同一 Schema 校验，不能只保存一个标题。

### 6.5 进入汇报生成

按钮门禁：

- 至少一个已选问题；
- 每个要进入汇报的问题至少有一条已选策略；
- 所有关联问题仍有 confirmed 洞察证据。

门禁失败返回 `GATE_BLOCKED` 和具体原因，不只禁用按钮。

## 7. 页面四：汇报生成

### 7.1 Report 数据模型

新增：

```sql
CREATE TABLE IF NOT EXISTS reports (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    outline_json TEXT NOT NULL,
    content TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

默认六章：

```text
01 项目背景
02 场地现状
03 关键约束
04 核心问题
05 设计策略
06 待补调研
```

### 7.2 生成和读取汇报

新增：

```http
POST /api/projects/{project_id}/reports:generate
GET  /api/projects/{project_id}/report
```

生成必须只读取：

- 当前项目基础信息；
- confirmed 洞察；
- 已选择且有确认事实支持的问题；
- `selected=true` 策略。

生成时不能通过 RAG 引入未确认的新事实。

### 7.3 编辑结构和草稿

新增：

```http
PATCH /api/reports/{report_id}
```

支持最小编辑范围：

- 章节标题；
- 章节顺序；
- 章节显隐；
- 汇报正文。

第一版不做复杂富文本编辑器，使用 textarea 或 contenteditable 即可。

### 7.4 Markdown 导出

调整为：

```http
POST /api/reports/{report_id}/export/markdown
GET  /api/exports/{export_id}/download
```

导出已保存的 Report，而不是每次点击时重新生成一份可能不同的内容。

成功返回：

```json
{
  "export": {
    "id": "...",
    "filename": "滨水文化中心改造-前期分析.md",
    "download_url": "/api/exports/.../download"
  }
}
```

前端不得展示后端绝对 `path`。

## 8. RAG 当前阻断问题

`app/services/rag.py` 的 `retrieve_project_context()` 当前存在变量引用错误：

- 正常分支在定义 `raw_chunks` 前使用它；
- 降级分支在定义 `text_chunks` 前使用它。

必须先修复并增加测试。

另外，当前上传阶段会写入 Chroma，但问题和策略 Agent 尚未调用 `retrieve_project_context()`。完成 RAG 的标准是：

```text
确认洞察/选中问题
→ 构造检索 query
→ 按 project_id 检索 Top K
→ 返回文件名、定位和原文
→ 将检索片段交给问题/策略 Agent
→ task_logs 记录检索数量和 rag_status
```

资料提取仍遍历全部 Chunk，不能只检索 Top K，避免遗漏任务书关键约束。

RAG 失败时使用 SQLite 原始 Chunk 降级，并明确标记：

```text
rag_status=degraded
retrieval_source=sqlite_raw_chunks
```

不得把降级称为向量检索。

## 9. 数据库迁移要求

现有数据库已经存在。仅修改 `CREATE TABLE IF NOT EXISTS` 不会增加新字段。

实现一个幂等迁移函数：

```text
读取 PRAGMA table_info(table)
→ 判断字段是否存在
→ 缺少时执行 ALTER TABLE ADD COLUMN
→ 重复启动不报错
```

迁移不得清空现有 SQLite 数据。

## 10. 前端文件建议

继续使用原生前端，但不要把全部逻辑继续堆在一个 HTML 内。

建议：

```text
app/static/
├─ index.html
├─ styles.css
└─ js/
   ├─ api.js
   ├─ store.js
   ├─ shell.js
   ├─ project-page.js
   ├─ review-page.js
   ├─ strategy-page.js
   └─ report-page.js
```

职责：

- `api.js`：统一请求、错误解析、超时；
- `store.js`：当前 project_id 和临时 UI 状态；
- 页面文件：只负责渲染和事件；
- 项目、卡片和选择结果必须从服务端恢复，不能把 localStorage 当业务数据库。

视觉实现以四张设计图为准。不要重新设计颜色、布局或信息架构。

### 阶段 A：阻断修复

1. 修复 RAG 检索变量错误；
2. 为新增字段实现 SQLite 幂等迁移；
3. 隐藏 API 响应中的绝对路径。

### 阶段 B：页面一和二

1. 项目更新；
2. 文件查看、重试、删除；
3. 任务日志读取；
4. 来源 Chunk 定位；
5. 项目资料与资料审核页面落地。

### 阶段 C：页面三

1. 问题选择持久化；
2. 策略按问题单选；
3. 自定义策略 CRUD；
4. 问题与策略页面落地。

### 阶段 D：页面四

1. Report 表和 Schema；
2. 生成、读取、编辑汇报；
3. 从已保存 Report 导出 Markdown；
4. 汇报页面落地。

### 阶段 E：联合验收

使用全新项目完成图形浏览器真实点击：

```text
填写项目资料并保存
→ 上传 TXT/MD + 图片
→ 查看解析和 RAG 状态
→ 生成洞察
→ 修改一张卡并再次确认
→ 驳回一张卡
→ 标记一张待核实
→ 生成并选择问题
→ 生成三条策略
→ 选择一条并验证同问题单选
→ 创建并编辑一条自定义策略
→ 生成汇报
→ 编辑章节结构和正文
→ 导出并下载 Markdown
→ 刷新和重启服务后验证状态恢复
```

同时验证：

- 没有 confirmed 洞察时问题生成被拦截；
- 没有选中策略时汇报生成被拦截；
- 未确认洞察和未选策略不出现在汇报；
- 关闭 Ollama 后主闭环可降级运行；
- DeepSeek Key 不出现在日志、前端、截图或 Git；
- 项目 A 的资料不能在项目 B 的 RAG 结果中出现。

## 12. 每阶段交付格式

每个开发阶段完成后必须返回：

```text
改动文件

数据库迁移内容
```

## 13. 给开发对话的开场指令

```text
请先完整阅读 docs/前端四页面开发交接.md，再检查当前代码与四张设计图。

严格按照文档的阶段 A → B → C → D → E 推进。先修阻断问题，再扩展接口，最后实现页面。不要推翻现有可运行闭环，不要更换技术栈，不要加入登录、云部署或与四个页面无关的功能。

以最快跑通和可验收为目标。每完成一个阶段先运行该阶段测试，再进入下一阶段；发现文档与当前代码冲突时，以现有真实数据安全、confirmed 门禁和最终汇报不引入未确认事实为最高原则。

不要输出、记录或提交 .env 中的 Key。不要删除现有 SQLite 数据。不要把 demo_fallback、SQLite 原始片段降级描述为真实模型或向量检索。

现在从阶段 A 开始，先报告检查结果，然后直接完成阶段 A 的最小修复与验收。
```
